# Baseline inventory, 2026-09-29

This is a read-only audit of all eight `trueseal-*` repositories, taken at their `main` HEADs on 2026-09-29. It is the evidence base for the Developer Preview map.

Status key:
- **Confirmed**: reproduced by a test or a direct run.
- **From code**: reasoned from the source. Treat it as a hypothesis until a test reproduces it.

## Cross-cutting findings

### Wire-protocol versioning: none
- Frames are `[type u8][len][body]` with no version. The Noise prologue is empty. The Envelope proto has no version field.
- Unknown frame types and message tags are silently dropped. On the client, a message that fails to decode is dropped *after* DeliverAck, so the relay deletes it.
- The only implicit markers are the proto package `trueseal.sync.v0`, the HKDF info `"…addressed encryption v0"` and `tsm1_` message IDs.
- There are no sync-level test vectors for Envelope, Manifest, addressed encryption or message IDs.

### Security defects
1. **Cross-inbox deletion (confirmed).**
   - The relay's `OnDeliverAck` deletes by `blob_id` without checking the recipient (`trueseal-relay/internal/relay/router.go:67-70`; `sqlite/store.go:117`; `postgres/store.go:152`).
   - Blob IDs are sequential, so any device with a receive session can wipe other inboxes.
2. **Concurrent encryption on the receive session (confirmed under `-race`).**
   - The delivery goroutine and the heartbeat reply both call `cs2.Encrypt` and write concurrently (`internal/session/receive.go:97,131`).
   - Clients fail to decrypt, 11 to 45 times per run in the repro.
3. **Joiner manifest trust (from code).**
   - `join_group` discards the initiator's signing key from the token (`trueseal-sync/src/session/mod.rs:357-369`).
   - With no local manifest, the client accepts `incoming.verify(None)`, which only checks self-signature (`mod.rs:236-239`, `manifest.rs:95-121`).
   - The member filter is skipped while the manifest is `None` (`mod.rs:199-206`).
   - Consequence: anyone who can address the device, including the relay and anonymous NK pushes, can install an attacker group. The legitimate group is later rejected with `GroupIdMismatch`.
4. **Pair body `signing_pub` is not bound to the envelope signer** (`mod.rs:170`, from code).
5. **Destroy Group Revoke is fire-and-forget, and any member can send it**, including a stolen device (`mod.rs:786-816`).

### Metadata and privacy
- The relay logs client IPs (`trueseal-relay/cmd/.../main.go:138,156,171`), which contradicts relay ADR-0011.
- The relay logs a 4-byte recipient key prefix and the size of every push (`router.go:57`).
- The bundled Dozzle log viewer is unauthenticated and mounts `docker.sock`, so it exposes every container's logs. HAProxy `option tcplog` puts client IPs into those logs.
- Several Push frames in one anonymous NK session link recipients who share a group (the fan-out leak).
- Sizes and timing are visible to the relay. The docs concede timing but say "That's it."

### Delivery semantics
- DeliverAck is sent before decryption and before the app callback. A crash inside `on_message` loses the message.
- **Connect/subscribe race (from code):** `run_loop` starts before `subscribe()`, so an inbox flush in that window is acked with no callbacks registered.
- Failed pushes while connected are retried only after the next reconnect, so messages can be reordered.
- `PushRejected` and `PushFailed` are not separated in the replay loop, so a permanently rejected blob retries forever.
- Control-plane messages (Pair, Manifest, Revoke) are never queued (P1 TODOs at `mod.rs:805,928,1063`).
- **Size contract is broken.**
  - Sync declares `MAX_ENVELOPE_BYTES = 1 MiB`, but noise frames cap plaintext at 65,519 bytes and the relay defaults to 65,482.
  - Envelopes between about 64 KB and 1 MiB get stuck in the outbox forever.
- The relay discards an early blob if it arrives before the select; it is delivered on the next notify (`receive.go:80-87`, from code).

### Membership
- Equal-version concurrent manifests: the first one seen wins, and devices can fork permanently. There is no deterministic tiebreak and no convergence test.
- Key rotation is not a primitive; the only way to rotate is to wipe the store. `PairedList` (`src/revocation.rs`) is dead code.
- There is no leave operation in the FFI.

### Relay operations
- **No abuse limits.**
  - There are no read or handshake deadlines, so idle connections can exhaust the 1000-slot cap.
  - There is no per-inbox quota or push rate limit.
  - Every notify re-sends the whole un-acked inbox.
- **Graceful shutdown doesn't cancel open sessions:** the session context is `context.Background()`.
- **`/healthz` always returns 200**, and there are no metrics.
- **`-genkey` is broken under Docker** (confirmed). The entrypoint doubles the binary path, so the flag is ignored.
- **Docs drift:** `config/relay.toml` is missing, two ADRs are numbered 0010, and ADR-0008 still claims 1 MiB and relay-initiated heartbeats.
- **Release process isn't enforced:** the old v1.0.0 was tagged on red CI, the deploy to the VPS failed, and the GHCR image `v1.0.0` still exists.

### SDK parity
| Area | Swift | Kotlin | TS |
|---|---|---|---|
| Relay address | `URL`; the port is silently ignored | `relayHost: String` | `relayHost: string` |
| Lifecycle | throwing `init` | constructor, `Closeable` | `static async create()`, `dispose()` |
| Send | `publish(_:) async throws` | `publish(ByteArray)` (sync) | `send(blob): Promise` |
| Pairing token | `generatePairingToken()` | `generatePairingToken()` | `pairingToken()` |
| removeMember | `SyncMember` | `SyncMember` | `memberId: string` |
| Events | 4 `AsyncStream`s | 4 `Flow`s | EventEmitter with 7 string events |
| Errors | typed enum (8) | sealed class (8) | a single untyped `TruesealSyncError(message)` |
| Core pin | tag v0.5.0 | `releases/latest` | sibling path |

- **TS duplicates core wiring.** It re-implements session wiring in its own `src/session.rs` instead of using core `ffi.rs`, so the two drift.
- **Docs disagree across SDKs:**
  - Swift documents a 60-second pairing window. Core ADR-0021 says there is no expiry.
  - After Destroy Group, Swift and TS give different rebuild instructions.
- **The six open TS issues (#1 to #6) are stale.** The work is done; the unmet packaging criteria should move to a new issue.

Harness weaknesses:
- CI checks out sibling default-branch HEADs, so a run is not reproducible against the artifacts being released.
- There is no single command that runs every lane.
- The README's release-gate table is a manual policy; nothing enforces it.

### Public docs claims that overreach
- "Compromise the relay… ciphertext and some recipient public keys. That's it." (`introduction.mdx:21-23`). Sizes, timing, IPs and fan-out are also visible.
- "No communication graph" (`principles-and-boundaries.mdx:16`), and "structurally unknowable" membership in the relay README.
- "Replay an old sequence number — and the signature stops matching" (`zero-trust-and-encryption.mdx:51`). A byte-identical replay keeps a valid signature.
- Destroy Group is called a "cryptographic guarantee that nothing future ever lands" (`concepts/revocation.mdx`). Revoke is best effort.
- "Guaranteed outbox replay". It is bounded by the TTL, by local database loss and by the size cap.
- Swift is called "Production-ready" (`sdks.mdx:19`). Kotlin is listed as "Available" with JVM support; it is Android-only and not installable.
- The docs name the example apps "trueseal-clip". Their real name is hush-clip.
- 1 MiB limit (`protocol/wire-format.mdx:115-121`). The effective limit is about 64 KB.
- There is no forward-secrecy statement for data at rest, which uses static-recipient DH.
- There is no threat model page, no versioning or support policy, and no stability statement.
